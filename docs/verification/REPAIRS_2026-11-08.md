# Ali Educational repair report

Date: 8 November 2026. Baseline: commit `e76327d`, app 1.0.13, database schema 8.

## Scope and safety

Repairs were developed in `tmp/repair-current` and built in the isolated `AliRepair20261108` temporary folder. Tests use the debug application and disposable emulator `emulator-5556`. No production phone was installed, uninstalled, reset or restored. No signing credentials were copied into this report. Existing business records have not been retrospectively rewritten or guessed.

This report distinguishes repaired behavior from release acceptance and features that still need work. It does not certify that every possible workflow is correct.

## Financial and inventory corrections

- Receiving goods keeps the newly calculated stock quantity, weighted cost and selling price together; a stale product object no longer overwrites stock.
- Editing product details starts with zero additional stock, preventing accidental duplication of existing quantities.
- Purchases allocate transport using unique purchase-line identities, including repeated products on the same invoice. Single-item purchases now include line records.
- Pack checkout separates the number of packs, their piece conversion, exact line charge and base-stock deduction. Conversion snapshots also drive receipt quantities and prices. Old receipts without a conversion snapshot retain base-piece quantities rather than inventing pack counts.
- Sale boundaries reject negative quantities/prices, missing customers for unpaid balances, nonexistent/archived products, overselling, duplicate line identities and repeated checkout of already-posted lines.
- Cash tender is preserved so change can be calculated. Payment-form repeated taps are guarded.
- Customer and supplier repayments allocate to outstanding bills/invoices in one database transaction. Bill dues now agree with account settlement. Allocation evidence is retained. Settlement followed by full bill cancellation reconciles remaining customer debt and money refunded.
- Damaged returns increase damaged stock without deducting sellable stock a second time.
- Customer and supplier history is archived instead of deleted, and outstanding accounts cannot be archived. Cancelling sales remains visible in history.
- Savings-linked cash edits update the same savings transaction. Deposit edits/cancellations and withdrawals cannot create a negative tracked scheme balance. Refunds cannot exceed their source expense; an expense with active refunds cannot be cancelled through an alternate API.
- Amount parsing rejects negative, malformed and overflowing values. Proportional allocation avoids intermediate integer overflow, and calculations reject unsupported totals instead of wrapping.

## Profit, expenses, reports and receipts

- Product profit excludes unknown-cost lines and displays an incomplete-profit warning. Historical cost snapshots are retained instead of recalculating past costs from current stock.
- Product charts use product lines rather than whole mixed product/service bills. Date grouping includes the year. Summary-only sales are excluded from product trend calculations.
- Negative inventory quantities no longer offset valid inventory asset value. Potential losses on stock priced below cost are no longer clamped away.
- Shop Expenses presents operating expenses and linked refunds from shared records, excluding savings transfers, with gross/refund/net totals. The export includes refunds and preserves cancelled/archived records where appropriate.
- The manual cash register's net is labelled **Register Net**. It is not represented as complete cash-in-hand: automatic sales receipts and account payments are still separate sources.
- Opening an old receipt loads its stored bill and timestamp, rather than the most recent checkout state. Pack display is shared by the receipt screen and generated receipt.

## Backup and recovery corrections

- Database snapshots are created from a consistent database transaction rather than copying a live SQLite file without its WAL.
- The archive includes the database, supported app preferences and attachment hashes. Missing referenced attachments prevent a misleading successful complete backup.
- Archive extraction rejects path traversal, duplicate entries, oversized packages and excessive nesting. Checksums, SQLite integrity, supported versions and actual Room schema validation run in staging before restore.
- A stored Room identity hash is not accepted as proof that the actual table structure is intact.
- Restore uses a live database transaction, preserving usable DAOs; it does not close Room and overwrite its active file. Attachments receive new names and their database references are remapped. A failed restore rolls back records/preferences and removes newly copied files. A pre-restore database safety snapshot is retained.
- Supported settings include shop name, theme, app/receipt language values, receipt action, text size, lock timeout and usual savings amount. Device roles, pairing tokens, private keys, owner PIN and document-provider permissions are deliberately not portable authorization credentials.
- External copy failures are reported separately from local completion. External saves reopen the target and compare SHA-256 before recording success.
- The connected-folder implementation still uses Android's document provider. A provider readback verifies the bytes it exposes; it does not prove that a cloud provider has finished uploading them remotely.

## Permissions and two-phone synchronization

- Replaced plaintext transport with TLS and an out-of-band pinned owner certificate. Tokens are randomly generated; the shared default token is rejected. Rotation revokes the old token.
- Removed the universal owner PIN. Owner PINs use salted PBKDF2, with persisted failed-attempt throttling. Switching to Billing requires a configured owner PIN; promotion requires authorization.
- Startup waits for lock settings; owner-only routes fail closed while the role loads. Hosting requests recheck owner authorization. Only Billing devices can ingest the owner catalog.
- UTF-8 request bodies are read by byte count, with header/body limits and socket timeouts.
- Bill ingestion, inventory changes, new customer creation and customer dues commit atomically. Duplicate identical bill delivery is acknowledged without double posting; conflicting identities are rejected. Acknowledgements must match the exact submitted sale IDs.
- Pending local quantities are accounted for when refreshing stock. New offline credit customers and barcode aliases are carried with synchronization. Conflicting barcode mappings are rejected.
- Owner-issued encrypted cost quotes preserve catalog-time cost without exposing cost plaintext in the Billing catalog. Invalid/unavailable quotes remain unresolved rather than being substituted with today's cost. These quotes reflect the last owner catalog snapshot, not a magically current cost while disconnected.
- Device-bound cost-quote keys are not exported. After a device replacement, older queued quotes may need explicit cost reconciliation.

## Workflow and layout corrections

- Added a visible multi-item supplier-invoice entry point and observable purchase-row fields.
- Added both clearly labelled Gross Margin and Markup pricing modes, with reverse calculation from selling price.
- Barcode generation uses collision-resistant identifiers, preserves manufacturer codes, and supports separate piece/pack aliases. Stock scanning resolves the product and asks for quantity. Linking an unknown code leads to quantity confirmation rather than silently adding one.
- Global app text-size scaling now applies to explicit text sizes too. Typing hints capitalize words in relevant names/notes without rewriting stored identifiers.
- Accounts navigation from bill history selects the customer tab/search. Existing Home history and widget action routes are regression-tested.
- Light-mode Accounts at Extra Large text and the stock form were visually inspected. A wrapping wholesale label was shortened. This is not a complete device/keyboard/TalkBack visual matrix.

## Tests and evidence

The baseline audit had 21 failures in 26 independent database checks. Those 26 checks pass after repair. The pack test fixture was corrected to give its database product the same 10-piece pack conversion already used by its draft; an explicit conversion is also now passed by checkout. Original audit evidence was retained unchanged.

Additional coverage includes complete application-table snapshot round trip, database/settings recovery, corrupted-archive rejection without live changes, duplicate checkout, payment then cancellation, purchase-line creation, import replay, savings constraints, owner promotion, pinned TLS, Urdu text transmission, offline customer credit and duplicate encrypted delivery. JVM tests also cover large-value allocation, overflow, pricing modes and pack receipt presentation.

Final totals and exact source-transfer status are recorded in `STATUS.md`, `unit-summary.json`, `repair-build.log`, `repair-instrumentation.txt`, `changed-files.json` and `promotion-result.json` when present. Logs from an earlier run must not be taken as proof for subsequent untested edits.

## Remaining work and release gates

The following are not claimed complete merely because regression tests pass:

1. Exact signed release APK upgrade rehearsal with representative old production data, including every attachment and pending sync state. Match package/signature, increment version, preserve data and compare financial totals before distributing to the brother's phone.
2. Physical Samsung widget resize, real camera/printed-barcode scans, actual printer output and real Drive permission/network/revocation tests.
3. Full two-physical-device lifecycle testing, including app termination during delivery, network loss and simultaneous owner/billing changes. Per-device pairing/revocation and a durable scheduled retry queue are more complete than the current shared pairing token plus manual retry.
4. Complete purchase correction/reversal, partial item returns, and account-payment reversal workflows need a dedicated ledger lifecycle; the repaired existing flows do not create those missing screens.
5. A unified cash/bank/UPI ledger must reconcile sales, purchases, settlements, refunds, operating expenses and transfers without duplicate counting. Register Net intentionally does not claim to be that ledger.
6. Direct authenticated Drive integration and durable background upload retries are not implemented by choosing a document-provider folder.
7. Full Urdu UI localization and the conversational Urdu AI assistant are not implemented by adding widget translations. The existing English UI decision was not silently reversed.
8. Review remaining lint warnings and broaden accessibility/contrast checks on populated screens and narrow devices. Passing lint means no lint errors, not zero warnings.
9. Previously corrupted production transactions need a separate read-only reconciliation report and a reviewed correction plan. No automated repair should guess historical costs, payments or deleted relationships.

Recommended release decision: keep this as a repair candidate until the exact-APK migration, recovery and physical-device gates pass. Keep the old recovery package and do not uninstall the app to install an update.
